# Reliability audit — 2026-11-15

Baseline: `2318bb65bc0d13b562dc1cee755355e6690c142f` (`feat/atomic-writebatch-hardening`). This is an initial audit, not a production qualification.

## Findings requiring investigation

1. **WAL directory entry durability:** `DB::Impl` opens `active.wal` with `O_CREAT`, but does not explicitly fsync the parent directory after creation. A successful fsync of the WAL file alone does not necessarily persist a newly created directory entry across power loss. Process-crash tests cannot establish power-loss durability. Review supported filesystems and add fault-injection coverage before changing the guarantee.
2. **Incomplete tail versus damaged length:** replay treats a syntactically valid header with a payload longer than the remaining file as an interrupted trailing write, truncating the tail. Corruption of a record length can resemble this case before its CRC is checked; the existing format does not inherently distinguish the two. Assess fail-closed and format-versioning tradeoffs without claiming arbitrary corruption is always detected.
3. **I/O fault coverage:** a failed write or fsync poisons the instance, but actual ENOSPC/EIO/partial-write and directory-sync failures need controlled injected tests. A thrown write may have reached disk and its post-reopen status is uncertain; tests must not assume failed calls are always absent.
4. **Concurrency scope:** calls are serialized with a single mutex, and flush/compaction run synchronously. Any background-worker design must handle WAL lifetime, immutable state, file references, failure propagation and shutdown before claiming correctness.

Linux execution on the local Windows workstation is unavailable: WSL has no distribution and existing server SSH requires interactive authentication. GitHub Actions on the branch can provide Linux CI; it is not an actual server performance test. No background flush, compaction, block format, cache, performance gain or ENOSPC/EIO validation is claimed here.

# Background flush and recovery

One worker owns at most one immutable MemTable; the active map continues receiving writes. A write validates first, then holds the mutex while appending its WAL record and (in sync mode) fsyncing it and updating all keys in that record. At the threshold, the active map becomes immutable in O(1), with the current sequence captured as its durability fence. When the immutable slot is occupied and active is already at/above the threshold, subsequent writers wait before appending to WAL. A single accepted batch may exceed the threshold (batch limits still apply).

The worker builds and validates the immutable SST without the mutex. Reads consult active, immutable, then SST; Scan merges the active/immutable values before the existing ordered merge. The worker takes the mutex to publish a manifest referencing the SST, with `durable_seq` equal to the immutable fence, never the possibly newer active sequence. WAL truncation occurs only after the manifest is durable and the active MemTable is empty under the mutex; otherwise it is retained to avoid losing newer acknowledged writes. If writes never leave the active map empty, the single WAL can grow: this implementation has no segmented-WAL reclamation yet.

`Flush()` blocks new writers, waits for a pending immutable, freezes the active map and waits for its manifest commit; `sync_writes=false` only promises durability after this barrier succeeds. `Compact()` uses the same barrier, then currently compacts synchronously under the mutex; **background compaction is not yet implemented**. The destructor signals shutdown and joins the worker, draining any already-frozen map but not implicitly flushing active; use `Flush()` for a checked durability boundary. A worker failure poisons the instance, wakes waiters, and leaves WAL/manifest for reopen; background exceptions cannot be reported from the destructor. The caller must keep DB alive until its client threads finish.

The regression test stalls SST fsync using the Linux linker wrapper: it checks that Put/WriteBatch/Get/Scan can progress while SST I/O is blocked, that an additional writer is backpressured when both maps are full, and that a crash while a previous SST is in flight recovers later WAL-acknowledged writes. Existing crash, reference-model, and injected I/O tests remain enabled. This is not proof against power-loss behavior on every filesystem or against every possible concurrency interleaving.
